# Отчёт: сбор логов приложения в Victoria Logs

## Что сделано и зачем

Логи — это записи, которые приложение пишет во время работы: «пришёл запрос», «пользователь вошёл», «произошла ошибка». Пока приложение работает в Kubernetes, эти записи разбросаны по разным подам, и при перезапуске пода они пропадают. Чтобы их можно было искать и анализировать, нужна отдельная система хранения логов.

В этом задании:
1. Бэкенд приложения переведён на логи в формате JSON.
2. В тот же кластер minikube установлена Victoria Logs — база данных для логов с веб-интерфейсом vmui.
3. Настроена автоматическая доставка логов из подов в Victoria Logs.
4. В vmui выполнены четыре запроса к логам.

Общая схема:

```
под backend  ──пишет JSON в stdout──>  файл лога на узле  ──читает──>  Vector  ──отправляет──>  Victoria Logs  ──>  vmui (браузер)
```

## Установка Victoria Logs

Victoria Logs установлена через Helm — менеджер пакетов для Kubernetes. Helm-чарт — это готовый набор манифестов, который ставится одной командой. Использован официальный чарт `victoria-logs-single` (версия на один сервер).

Настройки чарта лежат в [`k8s/logging/values.yaml`](../k8s/logging/values.yaml):
- логи хранятся на постоянном диске размером 2 Gi и не пропадают при перезапуске пода;
- логи хранятся 7 дней;
- включён Vector — программа, которая доставляет логи (подробнее ниже).

Команды установки:

```sh
helm repo add vm https://victoriametrics.github.io/helm-charts/
helm install vl vm/victoria-logs-single -f k8s/logging/values.yaml
```

Чтобы открыть vmui в браузере, порт сервиса Victoria Logs пробрасывается на компьютер:

```sh
kubectl port-forward svc/<сервис Victoria Logs> 9428:9428
```

После этого vmui доступен по адресу `http://localhost:9428/select/vmui/`.

## Логи в формате JSON

Раньше бэкенд писал логи обычным текстом, например `INFO: 127.0.0.1 "GET /palettes" 200`. Такую строку человеку прочитать легко, а программе сложно: чтобы достать из неё статус ответа, нужно разбирать текст.

Теперь каждая запись — это одна строка JSON, где у каждого значения есть имя. Такие записи Victoria Logs раскладывает на отдельные поля, и по любому из них можно искать.

Пример записи (вывод `kubectl logs -l app=backend`):

```json
{"timestamp": "2026-10-13T13:18:27.689332+00:00", "level": "warning", "message": "request completed", "service.name": "palette-backend", "logger": "app", "request_id": "a73d55e89d85477ba75c937fc255d2f4", "method": "POST", "path": "/auth/login", "status": 401, "duration_ms": 2.04, "user_id": null}
```

Эта запись означает: в 13:18 по UTC пришёл запрос `POST /auth/login`, сервер ответил 401 (неверный пароль) за 2 мс, пользователь не авторизован.

| Поле | Что означает |
|---|---|
| `timestamp` | когда произошло событие (время UTC) |
| `level` | важность: `info` — всё хорошо, `warning` — ошибка со стороны клиента (404, неверный пароль), `error` — ошибка сервера (5xx) |
| `message` | короткое описание события |
| `service.name` | какой сервис написал запись: `palette-backend` |
| `logger` | какая часть кода написала запись: `app`, `app.auth`, `uvicorn.error` |
| `request_id` | уникальный номер запроса; он же возвращается клиенту в заголовке `X-Request-ID` |
| `method`, `path`, `status`, `duration_ms` | метод, адрес, код ответа и время обработки запроса |
| `user_id` | id пользователя, если он вошёл в аккаунт; `null` для гостя |
| `event` | событие входа: `register`, `login`, `login_failed` |

Где это в коде:
- [`backend/app/logging_config.py`](../backend/app/logging_config.py) — превращает каждую запись в строку JSON;
- [`backend/app/main.py`](../backend/app/main.py) — middleware, то есть код, который срабатывает на каждый запрос и пишет о нём одну запись;
- [`backend/app/routers/auth.py`](../backend/app/routers/auth.py) — записи о регистрации и входе.

Дополнительно:
- запросы к `/health` не записываются: Kubernetes проверяет этот адрес каждые 5 секунд, и такие записи заглушили бы полезные;
- стандартные текстовые логи uvicorn (веб-сервера) отключены, чтобы записи не дублировались;
- пароли и email в логи не попадают.

## Доставка логов: почему Vector

Kubernetes сохраняет всё, что под пишет в stdout, в файлы на узле кластера (папка `/var/log/pods`). Vector запущен как DaemonSet — это значит, что на каждом узле работает ровно один его под. Он читает эти файлы, добавляет к каждой записи информацию о том, из какого пода она пришла (`kubernetes.pod_name`, `kubernetes.container_name`), разбирает JSON на поля и отправляет всё в Victoria Logs.

Поля из JSON приложения Vector сохраняет с приставкой `log.`: в запросах они называются `log.level`, `log.path`, `log.duration_ms`. Поле `message` становится стандартным полем `_msg`.

Почему выбран этот способ:
- **приложение ничего не знает о доставке.** Оно просто пишет в stdout, а логи собирает отдельная программа. Если поменять систему хранения логов, код приложения менять не нужно;
- **новые поды подхватываются автоматически.** Если увеличить число реплик (`kubectl scale`), их логи тоже начнут приходить в Victoria Logs. Альтернатива — сайдкар (дополнительный контейнер-сборщик в каждом поде) — потребовала бы менять каждый Deployment;
- **ничего не нужно ставить отдельно.** Vector входит в Helm-чарт Victoria Logs и уже настроен на отправку логов в неё.

## Запросы к логам (LogsQL)

LogsQL — язык запросов Victoria Logs. Все запросы выполнены в vmui за последние 15 минут. Перед этим был создан тестовый трафик: успешные запросы к `/openapi.json` (ответ 200), запросы к несуществующей странице (404) и попытки входа с неверным паролем (401).

### (а) Все записи бэкенда за последние 15 минут

```
_stream:{kubernetes.container_name="backend"}
```

![а](screenshots/a.png)

Показывает все записи из контейнера `backend` — всего 160 штук. Фильтр `_stream` выбирает записи по метаданным, которые добавил Vector, поэтому логи системных подов Kubernetes сюда не попадают. По подсветке INFO и WARN видно, что vmui распознал уровень каждой записи — значит, JSON разобран правильно.

### (б) Только предупреждения

```
log.level:warning
```

![б](screenshots/b.png)

Показывает только записи с уровнем `warning` — 120 штук. Это ответы 404 и 401, а также события «login failed». Так можно быстро найти все проблемные запросы и неудачные попытки входа.

### (в) Сколько запросов каждого уровня

```
log.path:* | stats by (log.level) count() as records
```

![в](screenshots/c.png)

Запрос считает HTTP-запросы и группирует их по уровню: 20 записей `info` (успешные ответы 200) и 40 записей `warning` (ответы 404 и 401).

Как читать запрос: `log.path:*` оставляет только записи о HTTP-запросах (только у них есть поле `path`), символ `|` передаёт их дальше, а `stats by (log.level) count()` считает количество в каждой группе. Так видно соотношение успешных запросов и ошибок.

### (г) Как быстро отвечает сервер

```
log.path:* | stats quantile(0.95, log.duration_ms) as p95_ms
```

![г](screenshots/d.png)

Результат — 2.91 мс. Это 95-й перцентиль времени ответа: 95% запросов обработаны быстрее 2.91 мс. Перцентиль удобнее среднего значения, потому что показывает время, которое получает почти каждый пользователь, и не искажается одним случайным медленным запросом.
