# Отчёт: логирование в Victoria Logs

## Развёртывание

Victoria Logs (single-node) развёрнута в том же minikube-кластере, что и приложение, официальным Helm-чартом `victoria-logs-single`. Значения чарта — [`k8s/logging/values.yaml`](../k8s/logging/values.yaml): постоянный том 2 Gi, хранение 7 дней, включённый Vector.

```sh
helm repo add vm https://victoriametrics.github.io/helm-charts/
helm install vl vm/victoria-logs-single -f k8s/logging/values.yaml
kubectl port-forward svc/<сервис Victoria Logs> 9428:9428   # vmui: http://localhost:9428/select/vmui/
```

## Формат логов

Бэкенд пишет одну JSON-запись на событие в stdout контейнера:
- форматтер — [`backend/app/logging_config.py`](../backend/app/logging_config.py);
- запись на каждый HTTP-запрос — middleware в [`backend/app/main.py`](../backend/app/main.py);
- события входа и регистрации — [`backend/app/routers/auth.py`](../backend/app/routers/auth.py).

Пример записи (`kubectl logs -l app=backend`):

```json
{"timestamp": "2026-10-13T13:18:27.689332+00:00", "level": "warning", "message": "request completed", "service.name": "palette-backend", "logger": "app", "request_id": "a73d55e89d85477ba75c937fc255d2f4", "method": "POST", "path": "/auth/login", "status": 401, "duration_ms": 2.04, "user_id": null}
```

| Поле | Значение |
|---|---|
| `timestamp` | время события, UTC, ISO 8601 |
| `level` | `info` (2xx/3xx), `warning` (4xx, неудачный вход), `error` (5xx, исключения) |
| `message` | текст события |
| `service.name` | `palette-backend` |
| `logger` | источник: `app`, `app.auth`, `uvicorn.error` |
| `request_id` | идентификатор запроса, также возвращается в заголовке `X-Request-ID` |
| `method`, `path`, `status`, `duration_ms` | параметры HTTP-запроса |
| `user_id` | id пользователя из JWT, `null` для гостя |
| `event` | `register`, `login`, `login_failed` |

Запросы к `/health` не логируются: их каждые 5 секунд выполняют пробы Kubernetes. Стандартный access-лог uvicorn отключён (`--no-access-log`), его заменяет middleware. Пароли и email в логи не пишутся.

## Доставка логов

Используется Vector из того же Helm-чарта, запущенный как DaemonSet. Vector читает файлы `/var/log/pods` на узле, добавляет метаданные Kubernetes (`kubernetes.pod_name`, `kubernetes.container_name`, метки пода), разбирает JSON из строки лога и отправляет записи в Victoria Logs. Поля из JSON приложения сохраняются с префиксом `log.` (`log.level`, `log.path`, `log.duration_ms`), поле `message` становится стандартным полем `_msg`.

Причины выбора:
- приложение не меняется: оно пишет в stdout, доставкой занимается отдельный компонент;
- один под Vector на узел собирает логи всех подов, включая новые реплики после `kubectl scale`; сайдкар пришлось бы добавлять в каждый Deployment;
- Vector поставляется вместе с чартом и уже настроен на Victoria Logs, отдельная установка шиппера не нужна.

## Запросы LogsQL

Все запросы выполнены в vmui с интервалом «Last 15 minutes». Трафик сгенерирован запросами к `/openapi.json` (200), к несуществующему пути (404) и неудачными попытками входа (401).

### (а) Сырые записи бэкенда за последние 15 минут

```
_stream:{kubernetes.container_name="backend"}
```

![а](screenshots/a.png)

Все записи из потока контейнера `backend` за выбранный интервал: 160 записей. `_stream` — фильтр по полям потока, которые Vector добавляет из метаданных Kubernetes, поэтому в выборку не попадают логи системных подов. Видно, что поле `level` распознано vmui: записи подсвечены как INFO и WARN.

### (б) Фильтр по полю: предупреждения

```
log.level:warning
```

![б](screenshots/b.png)

Только записи уровня `warning`: 120 записей. Это ответы 404 и 401, а также события `login failed`. Запрос показывает клиентские ошибки и неудачные попытки входа.

### (в) stats с группировкой по уровню

```
log.path:* | stats by (log.level) count() as records
```

![в](screenshots/c.png)

Число HTTP-запросов по уровням логирования: 20 записей `info` (ответы 200) и 40 записей `warning` (ответы 404 и 401). Фильтр `log.path:*` оставляет только записи о запросах (у них есть поле `path`), события `login failed` в подсчёт не входят. Показывает соотношение успешных запросов и ошибок за интервал.

### (г) Агрегация: 95-й перцентиль времени ответа

```
log.path:* | stats quantile(0.95, log.duration_ms) as p95_ms
```

![г](screenshots/d.png)

95% запросов за интервал обработаны быстрее 2.91 мс. Запрос показывает задержку бэкенда без учёта редких выбросов.
