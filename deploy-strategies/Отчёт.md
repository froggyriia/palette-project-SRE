# Отчёт: стратегии деплоя

Бэкенд приложения обновляется с версии `v1.0.0` до `v2.0.0` пятью способами: Rolling, Blue/Green, Canary, A/B и Shadow. Трафиком управляет Envoy Gateway (реализация Gateway API) в minikube.

| Стратегия | Механизм | Манифесты | Логи | Результат |
|---|---|---|---|---|
| Rolling | замена подов одного Deployment | [`strategies/rolling/`](../k8s/deploy-strategies/strategies/rolling) | [шаги](logs/rolling-steps.log), [трафик](logs/rolling-traffic.log) | поды заменены по одному, ошибок во время обновления и отката нет |
| Blue/Green | смена backend в HTTPRoute | [`strategies/blue-green/`](../k8s/deploy-strategies/strategies/blue-green) | [шаги](logs/blue-green-steps.log), [трафик](logs/blue-green-traffic.log) | 100% v1 → 100% v2 → 100% v1, переключение за один запрос |
| Canary | веса backend в HTTPRoute | [`strategies/canary/`](../k8s/deploy-strategies/strategies/canary) | [шаги](logs/canary-steps.log), [трафик](logs/canary-traffic.log) | 89/11 → 50/50 → 0/100 на 100 контрольных запросах |
| A/B | правило по заголовку в HTTPRoute | [`strategies/ab/`](../k8s/deploy-strategies/strategies/ab) | [шаги](logs/ab-steps.log), [трафик](logs/ab-traffic.log) | `x-user-group: beta` — 100% v2, остальные — 100% v1 |
| Shadow | фильтр `RequestMirror` в HTTPRoute | [`strategies/shadow/`](../k8s/deploy-strategies/strategies/shadow) | [шаги](logs/shadow-steps.log), [трафик](logs/shadow-traffic.log), [запросы подов](logs/shadow-requests.log) | пользователям отвечает только v1, v2 получила копию каждого запроса (150 из 150) |

Логи прогонов:

- `<стратегия>-steps.log` — шаги из `run.sh`: команды, поды с версиями, правила HTTPRoute и распределение 100 контрольных запросов по версиям после каждого шага;
- `<стратегия>-traffic.log` — непрерывный трафик из `traffic.sh`, около 5 запросов в секунду: время, версия и под, которые ответили;
- `shadow-requests.log` — запросы, дошедшие до подов, по их логам (`requests.sh`).

В начале каждого `traffic.log` есть ответы `HTTP-404`: `run.sh` удаляет маршрут предыдущей стратегии, и до применения нового HTTPRoute Gateway не знает, куда направить запрос.

## Доработка приложения

Чтобы бэкенд работал в нескольких подах и разные версии можно было различить, в приложение добавлено:

| Требование | Реализация |
|---|---|
| Состояние вне пода | Все данные (пользователи, палитры) хранятся в PostgreSQL. Сессии — JWT-токены, подписанные общим секретом `JWT_SECRET`: токен, выданный одним подом, принимает любой другой. Поэтому запросы одного пользователя может обслуживать любой под любой версии. |
| Readiness-проба | `GET /ready` выполняет `SELECT 1` в базе. Если база недоступна, ответ 503, и Kubernetes не отправляет на под трафик. |
| Liveness-проба | `GET /live` проверяет только то, что процесс отвечает. От базы не зависит, поэтому сбой базы не приводит к перезапуску подов. |
| Версия в ответе | `GET /version` возвращает `{"version": "v2.0.0", "pod": "<имя пода>"}`; каждый ответ API содержит заголовок `X-App-Version`. |
| Версия в метриках | Метка пода `version` попадает во все метрики через `labelmap` в конфигурации сбора VictoriaMetrics; дополнительно есть метрика `palette_build_info{app_version="..."}`. |
| Версия в логах | Поле `version` в каждой строке JSON-лога запроса. |

Версия задаётся переменной окружения `APP_VERSION`. Обе версии собраны из одного образа `palette-backend:1.1` и различаются только этой переменной и меткой `version`.

Код: [`backend/app/main.py`](../backend/app/main.py), [`backend/app/metrics.py`](../backend/app/metrics.py), тесты [`backend/tests/test_probes.py`](../backend/tests/test_probes.py). Основной бэкенд в namespace `default` тоже переведён на пробы `/live` и `/ready` ([`k8s/30-backend.yaml`](../k8s/30-backend.yaml)).

## Окружение

```
traffic.sh / run.sh (curl /version)
        │ port-forward :8888
        ▼
Envoy proxy (namespace envoy-gateway-system)  ← Gateway eg, GatewayClass eg
        │ правила HTTPRoute backend
        ├──▶ Service backend-v1 ──▶ поды v1.0.0 ─┐
        └──▶ Service backend-v2 ──▶ поды v2.0.0 ─┴──▶ PostgreSQL (db-0, namespace default)
```

- **Envoy Gateway v1.10.0** устанавливается вместе с CRD Gateway API. `GatewayClass eg` обслуживается контроллером Envoy Gateway, `Gateway eg` поднимает Envoy-прокси со слушателем HTTP :80. Ресурс `EnvoyProxy` уменьшает запросы ресурсов прокси, чтобы он поместился в minikube рядом с приложением и мониторингом ([`01-gateway.yaml`](../k8s/deploy-strategies/01-gateway.yaml)).
- **Namespace `deploy-demo`**: копии бэкенда для экспериментов. Основное приложение в `default` продолжает работать; копии используют его базу данных ([`00-namespace.yaml`](../k8s/deploy-strategies/00-namespace.yaml)).
- **HTTPRoute `backend`** — единственный ресурс, который меняется в Blue/Green, Canary, A/B и Shadow. Обе версии при этом уже запущены.
- **Доступ**: на minikube у LoadBalancer нет внешнего IP, поэтому скрипты делают port-forward на сервис Envoy-прокси. По той же причине Gateway остаётся в состоянии `PROGRAMMED False` (нет адреса), что не мешает Envoy-прокси принимать трафик.
- **Плавное удаление подов**: у подов есть `preStop: sleep 5`. После команды на удаление под ещё 5 секунд обслуживает запросы, пока Envoy исключает его из списка бэкендов. В пробном прогоне без этой задержки один запрос попал на завершающийся под и получил 503.
- **Мониторинг**: поды `deploy-demo` собирает VictoriaMetrics. Дашборд Grafana «Стратегии деплоя: версии бэкенда» показывает доли запросов, RPS, число подов, ошибки и задержку по версиям ([`deploy-strategies-dashboard.json`](../k8s/monitoring/grafana/deploy-strategies-dashboard.json)).

### Запуск

```sh
cd ~/palette-project/k8s/deploy-strategies
./setup.sh                 # образ 1.1, Envoy Gateway, namespace и Gateway
./traffic.sh canary        # терминал 1: непрерывный трафик через Gateway
./run.sh canary            # терминал 2: шаги стратегии, Enter между шагами
```

`run.sh` перед началом удаляет приложения и маршрут предыдущей стратегии (`reset.sh`), затем по шагам применяет манифесты. После каждого шага он выводит поды с версиями, правила HTTPRoute и распределение 100 запросов по версиям.

## Rolling

Один Deployment `backend` на 4 пода, Service выбирает поды всех версий. Новая версия задаётся изменением `APP_VERSION` и метки `version` в шаблоне пода. Kubernetes заменяет поды по одному: `maxSurge: 1` поднимает один под новой версии, `maxUnavailable: 0` запрещает удалять старый под, пока новый не прошёл readiness-пробу.

Шаги: развернуть v1 → применить v2 → откатить командой `kubectl rollout undo`.

**Результат** ([шаги](logs/rolling-steps.log), [трафик](logs/rolling-traffic.log)):

| Время | Событие | Ответы в трафике за 10 с с этого момента (v1 / v2) |
|---|---|---|
| 19:33:10 | v1 развёрнута, 4 пода | 43 / 0 |
| 19:33:18 | применена v2 | |
| 19:33:30 | готов первый под v2 | 35 / 8 |
| 19:33:50 | половина подов заменена | 17 / 25 |
| 19:34:20 | все 4 пода на v2 | 1 / 42 |
| 19:34:26 | `kubectl rollout undo` | |
| 19:34:40 | откат идёт | 23 / 20 |
| 19:35:10 | все 4 пода снова на v1 | 30 / 0 |

- Поды заменялись по одному примерно раз в 15 секунд: под v2 проходит readiness-пробу (начинается через 10 с) и `minReadySeconds: 5`, после этого удаляется один под v1.
- Пока шла замена, обе версии отвечали одновременно, и доля v2 росла по мере замены подов.
- После обновления 100 контрольных запросов обслужила v2, после отката — v1.
- За время обновления и отката нет ни одной ошибки. Девять ответов `HTTP-503` в 19:33:01–03 пришлись на первое развёртывание: маршрут уже был создан, а поды ещё не прошли readiness-пробу.
- Откат `rollout undo` тоже постепенный и занял около 45 секунд.
- `kubectl rollout undo` предупреждает, что не обновляет аннотацию `last-applied-configuration`. Поэтому при работе через `kubectl apply` откат надёжнее делать повторным применением манифеста предыдущей версии.

## Blue/Green

Обе версии запущены по 2 пода. Green (v1) получает весь трафик, blue (v2) прогрета и ждёт. Переключение — один `kubectl apply` HTTPRoute с другим backend, откат — обратное переключение.

Шаги: развернуть обе версии → весь трафик на green → переключить на blue → откат на green.

**Результат** ([шаги](logs/blue-green-steps.log), [трафик](logs/blue-green-traffic.log)):

| Время | Шаг | 100 контрольных запросов |
|---|---|---|
| 19:37:04 | v1 и v2 запущены по 2 пода, маршрута нет | — |
| 19:37:17 | маршрут на green | v1 — 100% |
| 19:37:26 | переключение на blue | v2 — 100% |
| 19:37:35 | откат на green | v1 — 100% |

В трафике смена версии происходит между двумя соседними запросами (интервал 0,2 с): до переключения отвечает только v1, после — только v2, смешанных ответов нет. Откат так же мгновенный: поды green всё время работали, менялось только правило маршрута.

## Canary

Обе версии запущены, HTTPRoute делит трафик весами `weight`. Доля v2 повышается в три шага: 90/10 → 50/50 → 0/100.

**Результат** ([шаги](logs/canary-steps.log), [трафик](logs/canary-traffic.log)):

| Время | Веса v1/v2 | 100 контрольных запросов | Трафик на этом шаге (v1 / v2) |
|---|---|---|---|
| 19:39:49 | 90 / 10 | v1 — 89, v2 — 11 | 46 / 3 |
| 19:39:58 | 50 / 50 | v1 — 50, v2 — 50 | 15 / 15 |
| 19:40:05 | 0 / 100 | v2 — 100 | 1 / 37 |

Envoy выбирает backend для каждого запроса случайно с учётом весов, поэтому на 100 запросах доля близка к весу, но не обязательно равна ему (89/11 при 90/10). Один ответ v1 на шаге 0/100 пришёлся на первую секунду после применения маршрута, пока Envoy получал новую конфигурацию. В реальной раскатке между шагами смотрят на ошибки и задержку v2 на дашборде; при деградации вес v2 возвращают к 0.

## A/B

Аудитория выбирается заголовком: запросы с `x-user-group: beta` идут на v2, остальные — на v1. Правило с заголовком точнее правила по умолчанию, поэтому Envoy проверяет его первым.

**Результат** ([шаги](logs/ab-steps.log), [трафик](logs/ab-traffic.log)):

| Запросы | 100 контрольных запросов |
|---|---|
| без заголовка | v1 — 100% |
| `x-user-group: beta` | v2 — 100% |
| `x-user-group: alpha` | v1 — 100% |

В трафике каждая строка содержит два запроса: обычного пользователя и пользователя из группы beta. После применения маршрута все 79 строк имеют вид `regular: v1.0.0 | beta: v2.0.0`. Проверка с `alpha` показывает, что на v2 попадает только выбранная группа, а не любой запрос с этим заголовком.

Первые 16 строк лога (19:41:33–37), где обе группы получили v2, записаны до запуска `run.sh ab`: тогда ещё действовал маршрут 0/100 от Canary.

## Shadow

Пользователям отвечает v1. Фильтр `RequestMirror` отправляет копию каждого запроса на v2, Envoy отбрасывает её ответ. v2 получает реальную нагрузку без влияния на пользователей: это видно по её логам и по метрике `http_requests_total{version="v2.0.0"}`.

Чтобы видеть копии запросов, используется `requests.sh`: он читает логи подов обеих версий и выводит по строке на каждый запрос, запросы на v2 помечены `mirror copy`.

**Результат** ([шаги](logs/shadow-steps.log), [трафик](logs/shadow-traffic.log), [запросы подов](logs/shadow-requests.log)):

- После применения маршрута (19:55:46) все ответы пользователю пришли от v1: 100 контрольных запросов и весь трафик в `shadow-traffic.log` — только v1.
- По логам подов v1 обработала 150 запросов, v2 — тоже 150: каждый запрос пришёл на v2 копией. В `shadow-requests.log` строки v1 и v2 чередуются: на каждый запрос, обработанный v1, приходится копия на v2.
- `run.sh` по логам v2 насчитал 120 запросов к `/version` за 30 секунд — это копии запросов, ни один из которых не дошёл до пользователя.

Повторные заголовки `strategy: shadow` в начале `shadow-steps.log` — перезапуски скрипта перед записью, результат относится к последнему прогону (19:55:28).

## Сравнение

| Стратегия | Простой | Ресурсы | Откат | Контроль трафика |
|---|---|---|---|---|
| Rolling | нет | +1 под на время раскатки | `rollout undo`, тоже постепенно | нет: версии смешиваются |
| Blue/Green | нет | две полные копии | мгновенно, одним apply | всё или ничего |
| Canary | нет | две версии | быстро: вес v2 = 0 | доля запросов |
| A/B | нет | две версии | быстро: убрать правило | точная аудитория |
| Shadow | нет | две копии | не нужен: v2 не отвечает пользователям | копия трафика |

Итог по прогонам: самое быстрое переключение и откат у Blue/Green (один apply, без смешения версий), самый плавный ввод новой версии — у Canary, точный выбор аудитории — у A/B. Rolling не требует второго набора подов, но откат у него такой же постепенный, как обновление. Shadow проверяет новую версию на реальном трафике без риска для пользователей, но не заменяет её выкатку.
