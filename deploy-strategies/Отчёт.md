# Отчёт: стратегии деплоя

Бэкенд приложения обновляется с версии `v1.0.0` до `v2.0.0` пятью способами: Rolling, Blue/Green, Canary, A/B и Shadow. Трафиком управляет Envoy Gateway (реализация Gateway API) в minikube.

| Стратегия | Механизм | Манифесты | Лог | Видео |
|---|---|---|---|---|
| Rolling | замена подов одного Deployment | [`strategies/rolling/`](../k8s/deploy-strategies/strategies/rolling) | [`rolling`](logs/rolling-steps.log) | — |
| Blue/Green | смена backend в HTTPRoute | [`strategies/blue-green/`](../k8s/deploy-strategies/strategies/blue-green) | [`blue-green`](logs/blue-green-steps.log) | — |
| Canary | веса backend в HTTPRoute | [`strategies/canary/`](../k8s/deploy-strategies/strategies/canary) | [`canary`](logs/canary-steps.log) | — |
| A/B | правило по заголовку в HTTPRoute | [`strategies/ab/`](../k8s/deploy-strategies/strategies/ab) | [`ab`](logs/ab-steps.log) | — |
| Shadow | фильтр `RequestMirror` в HTTPRoute | [`strategies/shadow/`](../k8s/deploy-strategies/strategies/shadow) | [`shadow`](logs/shadow-steps.log) | — |

Для каждой стратегии записаны два лога: `<стратегия>-steps.log` (шаги, состояние подов, правила маршрута и распределение 100 контрольных запросов по версиям) и `<стратегия>-traffic.log` (непрерывный трафик: какая версия и какой под ответили на каждый запрос).

## Доработка приложения

Чтобы бэкенд работал в нескольких подах и разные версии можно было различить, в приложение добавлено:

| Требование | Реализация |
|---|---|
| Состояние вне пода | Все данные (пользователи, палитры) хранятся в PostgreSQL. Сессии — JWT-токены, подписанные общим секретом `JWT_SECRET`: токен, выданный одним подом, принимает любой другой. Поэтому запросы одного пользователя может обслуживать любой под любой версии. |
| Readiness-проба | `GET /ready` выполняет `SELECT 1` в базе. Если база недоступна, ответ 503, и Kubernetes не отправляет на под трафик. |
| Liveness-проба | `GET /live` проверяет только то, что процесс отвечает. От базы не зависит, поэтому сбой базы не приводит к перезапуску подов. |
| Версия в ответе | `GET /version` возвращает `{"version": "v2.0.0", "pod": "<имя пода>"}`; каждый ответ API содержит заголовок `X-App-Version`. |
| Версия в метриках | Метка пода `version` попадает во все метрики через `labelmap` в конфигурации сбора VictoriaMetrics; дополнительно есть метрика `palette_build_info{app_version="..."}`. |
| Версия в логах | Поле `version` в каждой строке JSON-лога запроса. |

Версия задаётся переменной окружения `APP_VERSION`. Обе версии собраны из одного образа `palette-backend:1.1` и различаются только этой переменной и меткой `version`.

Код: [`backend/app/main.py`](../backend/app/main.py), [`backend/app/metrics.py`](../backend/app/metrics.py), тесты [`backend/tests/test_probes.py`](../backend/tests/test_probes.py). Основной бэкенд в namespace `default` тоже переведён на пробы `/live` и `/ready` ([`k8s/30-backend.yaml`](../k8s/30-backend.yaml)).

## Окружение

```
traffic.sh / run.sh (curl /version)
        │ port-forward :8888
        ▼
Envoy proxy (namespace envoy-gateway-system)  ← Gateway eg, GatewayClass eg
        │ правила HTTPRoute backend
        ├──▶ Service backend-v1 ──▶ поды v1.0.0 ─┐
        └──▶ Service backend-v2 ──▶ поды v2.0.0 ─┴──▶ PostgreSQL (db-0, namespace default)
```

- **Envoy Gateway v1.10.0** устанавливается вместе с CRD Gateway API. `GatewayClass eg` обслуживается контроллером Envoy Gateway, `Gateway eg` поднимает Envoy-прокси со слушателем HTTP :80. Ресурс `EnvoyProxy` уменьшает запросы ресурсов прокси, чтобы он поместился в minikube рядом с приложением и мониторингом ([`01-gateway.yaml`](../k8s/deploy-strategies/01-gateway.yaml)).
- **Namespace `deploy-demo`**: копии бэкенда для экспериментов. Основное приложение в `default` продолжает работать; копии используют его базу данных ([`00-namespace.yaml`](../k8s/deploy-strategies/00-namespace.yaml)).
- **HTTPRoute `backend`** — единственный ресурс, который меняется в Blue/Green, Canary, A/B и Shadow. Обе версии при этом уже запущены.
- **Доступ**: на minikube у LoadBalancer нет внешнего IP, поэтому скрипты делают port-forward на сервис Envoy-прокси.
- **Мониторинг**: поды `deploy-demo` собирает VictoriaMetrics. Дашборд Grafana «Стратегии деплоя: версии бэкенда» показывает доли запросов, RPS, число подов, ошибки и задержку по версиям ([`deploy-strategies-dashboard.json`](../k8s/monitoring/grafana/deploy-strategies-dashboard.json)).

### Запуск

```sh
cd ~/palette-project/k8s/deploy-strategies
./setup.sh                 # образ 1.1, Envoy Gateway, namespace и Gateway
./traffic.sh canary        # терминал 1: непрерывный трафик через Gateway
./run.sh canary            # терминал 2: шаги стратегии, Enter между шагами
```

`run.sh` перед началом удаляет приложения и маршрут предыдущей стратегии (`reset.sh`), затем по шагам применяет манифесты. После каждого шага он выводит поды с версиями, правила HTTPRoute и распределение 100 запросов по версиям.

## Rolling

Один Deployment `backend` на 4 пода, Service выбирает поды всех версий. Новая версия задаётся изменением `APP_VERSION` и метки `version` в шаблоне пода. Kubernetes заменяет поды по одному: `maxSurge: 1` поднимает один под новой версии, `maxUnavailable: 0` запрещает удалять старый под, пока новый не прошёл readiness-пробу.

Шаги: развернуть v1 → применить v2 → откатить командой `kubectl rollout undo`.

_Результат будет добавлен после записи._

## Blue/Green

Обе версии запущены по 2 пода. Green (v1) получает весь трафик, blue (v2) прогрета и ждёт. Переключение — один `kubectl apply` HTTPRoute с другим backend, откат — обратное переключение.

Шаги: развернуть обе версии → весь трафик на green → переключить на blue → откат на green.

_Результат будет добавлен после записи._

## Canary

Обе версии запущены, HTTPRoute делит трафик весами `weight`. Доля v2 повышается в три шага: 90/10 → 50/50 → 0/100.

_Результат будет добавлен после записи._

## A/B

Аудитория выбирается заголовком: запросы с `x-user-group: beta` идут на v2, остальные — на v1. Правило с заголовком точнее правила по умолчанию, поэтому Envoy проверяет его первым.

_Результат будет добавлен после записи._

## Shadow

Пользователям отвечает v1. Фильтр `RequestMirror` отправляет копию каждого запроса на v2, Envoy отбрасывает её ответ. v2 получает реальную нагрузку без влияния на пользователей: это видно по её логам и по метрике `http_requests_total{version="v2.0.0"}`.

_Результат будет добавлен после записи._

## Сравнение

| Стратегия | Простой | Ресурсы | Откат | Контроль трафика |
|---|---|---|---|---|
| Rolling | нет | +1 под на время раскатки | `rollout undo`, тоже постепенно | нет: версии смешиваются |
| Blue/Green | нет | две полные копии | мгновенно, одним apply | всё или ничего |
| Canary | нет | две версии | быстро: вес v2 = 0 | доля запросов |
| A/B | нет | две версии | быстро: убрать правило | точная аудитория |
| Shadow | нет | две копии | не нужен: v2 не отвечает пользователям | копия трафика |
